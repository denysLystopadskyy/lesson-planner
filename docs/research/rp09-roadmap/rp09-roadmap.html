1. Executive summary

  • Order of operations is fixed and non-negotiable: dump the raw storage on every surviving device today; remove the published personal payment identifiers; guard the storage layer; ship a versioned JSON backup with a staleness nag. Nothing else starts before these.
  • Storage hardening and the JSON backup land in the legacy index.html. Cloud sync ships once, in the React app, after cutover — pulled forward only if the staleness indicator crosses 14 days twice.
  • The durable store is Firestore users/{uid} on Spark in europe-central2, plus client-rotated snapshots at users/{uid}/snapshots/{ts}, plus the local JSON envelope. Firestore alone is replication, never backup.
  • Auth is Google-provider only, signInWithPopup from a visible button, denyslystopadskyy.github.io on the authorized-domain list, rule request.auth.uid == uid. Never signInWithRedirect, never anonymous auth.
  • Migration follows RP-02 Strategy C: Vite + React + TypeScript, no router, base: '/lesson-planner/', staging at /lesson-planner/next/ writing prefixed storage keys. RP-02's P3 exit criterion is amended in §2 accordingly.
  • Land the diverged working copy of index.html, commit the toolchain, freeze the eight data-testid names as a contract React must reproduce, cap the DOM-level suite at its current size, drop the 17-file screenplay layer, and put every new test hour into the storage-contract layer.
  • Test layers kept: Playwright E2E on Chromium only, storage contract, and Vitest pure-function units. Dropped: jsdom component tests, pixel visual regression, cross-browser matrix, mutation testing, coverage thresholds.
  • The accessibility target is WCAG 2.2 Level AA. Target size passes; the 44×44 figure is Level AAA and out of scope. Remediation lands inside the React components, ranked fourth, not as patches to the legacy file.
  • Switching the Pages publishing source to GitHub Actions is a manual repository-owner action and a hard prerequisite for the build step. Never select main / /docs.
  • Never build: routing, payments, automated sending, student records, PDF invoices, portals, an i18n framework, CRDTs, Postgres, a subscribable calendar feed, or client-side encryption of group names.

4. Immediate-action block (data-loss and exposure risk)

Everything in this block is separated from the roadmap because it is either time-critical or a blocker on later work. Steps 1 to 4 need no code. Nothing may be uploaded, emailed, synced or placed in a shared folder until step 5 has landed — RP-05, RP-06 and RP-07 all say so independently, because the default template reaches every user who never edited it.

Today, in this order.

  1. Stop the fastest clock. On the affected machine: stop using it for anything that writes to disk, and disconnect the Time Machine disk so a fresh backup cannot age out the pre-incident snapshot. macOS local snapshots are kept roughly 24 hours; if more than a day has passed, that path is already closed.
  2. Run the raw storage dump on every device and browser that might hold data — second laptop, phone, tablet, work computer. It reads the three keys as raw strings and never parses them, so it survives corrupt data, and it needs no deploy. This is quick win QW-1 and it is the only action in the whole programme that can still save data that exists right now.
  3. Search for artifacts, not bytes. lesson-planner-*.csv on every device and in Downloads, mail and chat; the payment messages she already sent (they carry the month, lesson count and total per group, which reconstructs the money even if individual dates are gone); her own calendar or notebook. These two searches are more likely to pay off than anything involving browser internals.
  4. Send her one message with four questions. Which browser, device and operating system does she use — see §7, where one answer closes a cluster of unknowns. Did she ever click Save CSV, and where did those files go. How many groups and months did she keep. What exactly did "cleaning the laptop" mean. Do not bundle product questions into this message; it is a rescue message.

6. Critical path and droppable work

The critical path has two independent halves, and only the second is a chain.

The first half is R0 → R1 → R2. It is on the critical path for one reason: it is the only work that reduces the probability of another total loss, and every day it is not done is a day of exposure. It does not depend on any decision, any toolchain, any hosting change or any answer from anyone. It should be finished before R3 starts, and it is deliberately sequenced so that the single most exposed thing — a real IBAN and tax identifier on the public internet — is dealt with on day one rather than at the end of a refactor.
