## 1. Executive summary

- **Order of operations is fixed and non-negotiable:** dump the raw storage on every surviving device today; remove the published personal payment identifiers; guard the storage layer; ship a versioned JSON backup with a staleness nag. Nothing else starts before these.
- **Storage hardening and the JSON backup land in the legacy `index.html`.** Cloud sync ships **once**, in the React app, after cutover — pulled forward only if the staleness indicator crosses 14 days twice.
- **The durable store is Firestore `users/{uid}` on Spark in `europe-central2`, plus client-rotated snapshots at `users/{uid}/snapshots/{ts}`, plus the local JSON envelope.** Firestore alone is replication, never backup.
- **Auth is Google-provider only, `signInWithPopup` from a visible button**, `denyslystopadskyy.github.io` on the authorized-domain list, rule `request.auth.uid == uid`. Never `signInWithRedirect`, never anonymous auth.
- **Migration follows RP-02 Strategy C:** Vite + React + TypeScript, no router, `base: '/lesson-planner/'`, staging at `/lesson-planner/next/` writing **prefixed** storage keys. RP-02's P3 exit criterion is amended in §2 accordingly.
- **Land the diverged working copy of `index.html`, commit the toolchain, freeze the eight `data-testid` names as a contract React must reproduce, cap the DOM-level suite at its current size, drop the 17-file screenplay layer**, and put every new test hour into the storage-contract layer.
- **Test layers kept:** Playwright E2E on Chromium only, storage contract, and Vitest pure-function units. **Dropped:** jsdom component tests, pixel visual regression, cross-browser matrix, mutation testing, coverage thresholds.
- **The accessibility target is WCAG 2.2 Level AA.** Target size passes; the 44×44 figure is Level AAA and out of scope. Remediation lands inside the React components, ranked fourth, not as patches to the legacy file.
- **Switching the Pages publishing source to GitHub Actions is a manual repository-owner action and a hard prerequisite for the build step.** Never select `main` / `/docs`.
- **Never build:** routing, payments, automated sending, student records, PDF invoices, portals, an i18n framework, CRDTs, Postgres, a subscribable calendar feed, or client-side encryption of group names.

## 4. Immediate-action block (data-loss and exposure risk)

Everything in this block is separated from the roadmap because it is either time-critical or a blocker on later work. Steps 1 to 4 need no code. **Nothing may be uploaded, emailed, synced or placed in a shared folder until step 5 has landed** — RP-05, RP-06 and RP-07 all say so independently, because the default template reaches every user who never edited it.

**Today, in this order.**

1. **Stop the fastest clock.** On the affected machine: stop using it for anything that writes to disk, and disconnect the Time Machine disk so a fresh backup cannot age out the pre-incident snapshot. macOS local snapshots are kept roughly 24 hours; if more than a day has passed, that path is already closed.
2. **Run the raw storage dump on every device and browser that might hold data** — second laptop, phone, tablet, work computer. It reads the three keys as raw strings and never parses them, so it survives corrupt data, and it needs no deploy. This is quick win QW-1 and it is the only action in the whole programme that can still save data that exists right now.
3. **Search for artifacts, not bytes.** `lesson-planner-*.csv` on every device and in Downloads, mail and chat; the payment messages she already sent (they carry the month, lesson count and total per group, which reconstructs the money even if individual dates are gone); her own calendar or notebook. These two searches are more likely to pay off than anything involving browser internals.
4. **Send her one message with four questions.** Which browser, device and operating system does she use — see §7, where one answer closes a cluster of unknowns. Did she ever click Save CSV, and where did those files go. How many groups and months did she keep. What exactly did "cleaning the laptop" mean. Do not bundle product questions into this message; it is a rescue message.

**Day 1, and it blocks everything cloud-shaped.**

5. **Remove the personal payment identifiers from the default template** (`index.html:387-392` and the personal first name at `400`), fixing the template's `1 lessons` wording in the same edit, then **add the repository guard** that fails when IBAN-shaped or long-digit strings reappear. Treat the identifiers as **permanently disclosed** — they have been publicly readable since the first commit — and tell the named person so they can decide about the bank account. A git-history purge is optional mitigation afterwards, never remediation, and it must not delay the conversation. Quick wins QW-2 and QW-3.

**Weekend 1 — stop the next silent loss.**

6. **Guard the storage layer**: per-key try/catch around both `JSON.parse` calls, the unparseable value copied to `<key>.corrupt.backup`, a shape check before assignment, guarded `setItem`, and `init()` always completing. This closes the runtime-verified dead-page failure that is the most plausible mechanism for a repeat of the original loss. QW-4.
7. **Close the three ways the app corrupts or bricks its own data:** escape the group name in the card sink (verified script execution, and a credential-theft path the moment a signed-in session exists), constrain the year and price inputs, and sanitise the currency on import. QW-5, QW-6, QW-7.

**Weekend 2 — give her a backup that works.**

8. **Ship the versioned JSON envelope** covering all three keys, the **fingerprint utility** that makes any restore checkable, the **pre-destructive snapshot with an undo**, the **import confirmation naming both sides**, the **last-backup age indicator with a nag**, and the **persistent-storage request**. QW-8 through QW-14.
9. **Rehearse Procedure B end to end with her once, on purpose, while nothing is broken.** An unrehearsed restore is a hope. Do not hand her a procedure whose buttons do not exist yet — that is the prior-art failure this programme already documented.

## 6. Critical path and droppable work

**The critical path has two independent halves, and only the second is a chain.**

The first half is **R0 → R1 → R2**. It is on the critical path for one reason: it is the only work that reduces the probability of another total loss, and every day it is not done is a day of exposure. It does not depend on any decision, any toolchain, any hosting change or any answer from anyone. It should be finished before R3 starts, and it is deliberately sequenced so that the single most exposed thing — a real IBAN and tax identifier on the public internet — is dealt with on day one rather than at the end of a refactor.

The second half is **R3 → R6 → R8 → R9 → R10 → R11**. Each link is genuine. R3 freezes the file so line citations and commands stop being wrong. R6 produces the typed modules the skeleton's storage adapter is built from. R8 cannot start until D3 is answered, because the publishing-source flip is outside the code. R9 is the only L in the plan and the only step whose scope can silently grow. R10 is gated on R9's parity checklist having a disposition per row. R11 is gated on R10 because sync ships once, into the app that will still exist.

## 10. Top risks and mitigations

| # | Risk | Mechanism | Mitigation |
| --- | --- | --- | --- |
| K1 | **Abandonment mid-migration** — the single largest risk to the whole plan | One part-time engineer stalls, leaving two half-apps and a live site nobody dares touch | The plan is ordered so that every stall point is a working live site plus an unfinished experiment. R0 to R2 deliver the entire data-safety benefit before any React code exists, so the most valuable half of the programme cannot be lost to a stall. The staging path means the root URL is never mid-migration |
| K2 | **The personal identifiers reach a cloud copy, a backup file or a committed test fixture** | The default template reaches every user who never edited it, and it is carried by the JSON envelope, the Firestore document, every snapshot, and any approval test that uses the real template | Hard blocker, enforced three ways: R0 step 5 lands first; the committed grep guard fails the file if a shape reappears; and QW-21's acceptance criteria require the guard to pass **after** the diverged copy is merged, because that copy still contains the values. No upload, email or shared folder before R0 step 5 |
| K3 | **The staging build destroys the live data** | Same origin means `/lesson-planner/next/` shares `localStorage` with the live app, and an unfinished React build writing the three keys is a realistic data-loss event, not a theoretical one | Prefixed keys by default (C9); `scripts/assert-storage-keys.sh` fails the build if the cutover bundle does not reference all three unprefixed literals, and is skipped for staging builds; staging is seeded by importing an export, never by sharing keys; a fresh off-laptop export exists before the staging URL is opened on any machine |
| K4 | **Line-number drift silently invalidates the prompts** | QW-21 shifts every citation in nine reports by up to 18 lines. A prompt run against the wrong line edits the wrong thing and may still appear to succeed | QW-21 is positioned after every other `index.html` quick win. R3 carries an explicit task to re-verify citations in every unshipped prompt, with a done-when. The standing warning sits directly under the §9 heading. Where a prompt is run out of order, locate by symbol name |
| K5 | **The Pages publishing-source flip is declined or goes wrong** | It is a manual repository-owner action in the web UI that no script can perform, and the documentation does not say what happens to the live site during the switch | D3 is answered before R8 starts. Sequenced so the first Actions deployment publishes byte-identical content, making the flip content-neutral: if it works nothing changes, if it fails the developer is watching. Never select `main` / `/docs`, which would publish the research reports instead of the app |
| K6 | **Silent parity drift at R9** | The parity checklist is manual, and a missed inventory row is exactly the silent regression the migration exists to prevent. R9 is also the only L step and the only one whose scope can grow unnoticed | The exit criterion is "every row has a disposition", not "it looks done", and the checklist is committed. The dual-project report diff makes the outcome boolean. Accessibility and capability work are explicitly bucketed so scope creep is visible as a bucket violation |
| K7 | **Sync propagates corruption everywhere, with nothing to roll back to** | Spark has no scheduled backup, no PITR and no managed export. One bad write to `users/{uid}` syncs to every device | The snapshot layer is mandatory, not optional (C4): client-rotated documents, deterministic retention, restore via Procedure C. Validate `schemaVersion` and that `groups` is an array before assigning any remote document. The JSON envelope is an independent copy that predates any bad write |
| K8 | **A silent write failure the user cannot detect** | Firestore's latency compensation notifies local listeners before data reaches the server, so an indicator wired to the call site would show success during a total outage | The indicator advances only on `hasPendingWrites` becoming false or `waitForPendingWrites()` resolving. Acceptance criterion 19 requires a test that asserts the indicator does **not** advance while offline. Web offline persistence is off by default, so a boot-time fingerprint compare and push is required, not optional |
| K9 | **She never presses Save backup, so no independent copy exists** | The residual manual step cannot be removed: a page cannot write to an arbitrary path unattended, the file picker needs a user gesture and is not available in every engine | The staleness indicator with a warning past 14 days; the fact that the cloud layers make a missed file backup no longer a single point of failure; and the pull-forward trigger in C2 that promotes sync if the indicator crosses 14 days twice. Rehearse the restore once while nothing is broken |
| K10 | **Approving a defect into permanence** | The documented failure mode of approval testing: a snapshot is updated without review, and the wrong behaviour becomes the expected one. Six known-wrong behaviours are queued for change | Every approved file carries a contract-or-defect label naming the defect id. Every spec carries an INV / DEF / CHAR tag, reviewed with the developer **before** R9, not during it. A test that passes on both projects but is tagged DEF is itself a finding |
| K11 | **The migration is judged on the wrong axis and looks like a regression** | The bundled app will be heavier on the wire and slower to first paint than 13,610 gzipped bytes in one request. If performance is the stated benefit, the migration fails on its own terms | State the justification as maintainability, testability, and the removal of the XSS and unhandled-error defect classes. Never sell it as performance. Measure the bundle once and record the number rather than discovering it in an argument |
| K12 | **Capability work starts before the storage layer is safe** | The improvement backlog is attractive and the data-safety work is invisible. Three backlog items add fields to the persisted shape and therefore need the version key first | The version key ships in R2, and the three field-adding items are explicitly sequenced behind it in R12. Bucket discipline: nothing from bucket (ii) or (iii) starts while any R0 to R2 item is open |
| K13 | **Free-tier terms change, or the account becomes unusable** | The plan starts requiring a payment method, an inactivity policy appears, an employer administrator blocks third-party authorisation, or the project is deleted by mistake | The switching triggers are written down with the specific signal for each. The local path has no dependency to rot, and the JSON envelope is provider-independent. Note the honest position: the absence of a documented inactivity policy is the strongest statement the evidence supports, not a guarantee |
| K14 | **The restore procedures are never rehearsed and fail when needed** | An unrehearsed restore is a hope, and the prior art already shows the failure mode of handing over a procedure whose buttons do not exist | R2's done-when includes rehearsing Procedure B end to end with her. Procedures A and C are rehearsed at R11. Do not hand over any procedure before the controls it names exist |
| K15 | **A pulled-forward decision reintroduces a resolved conflict** | Under time pressure the easy moves are: ship sync into the legacy file, share the live keys with staging, or grow the DOM-level suite because the hooks now exist | Each is named as a resolved conflict with its reasoning in §2, so re-litigating it is at least visible. The two that carry data-loss risk — sync in the legacy file and shared staging keys — are also the two whose mitigations are machine-checked by the key gate |
